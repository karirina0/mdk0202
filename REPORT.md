# Отчёт о конфликте при слиянии и принятых решениях

## Состав команды и роли

| Участник   | Роль                          | Ветка                            |
|------------|-------------------------------|------------------------------------|
| Морозова К.А. | Архитектор / Tech Lead        | ревью PR, финальный мердж в `main` |
| Козлов И.И. | Backend Task Service          | `feature/tasks-service`            |
| Кубрак А.А. | Backend Notification Service  | `feature/notifications-service`    |

## Как проходила интеграция

Вся работа с git велась через веб-интерфейс GitHub (создание веток, загрузка файлов, Pull Request'ы — без использования терминала).

1. Tech Lead создал ветку `dev` от `main` и загрузил в неё `API_CONTRACT.md`.
2. Участник 2 и Участник 3, каждый под своим аккаунтом, создали ветки `feature/tasks-service` и `feature/notifications-service` от `dev` и загрузили в них папки своих сервисов.
3. Оба открыли Pull Request в `dev`. Tech Lead проверил оба PR (**Files changed → Review changes → Approve**) и смёржил их — **оба слились в `dev` без конфликтов**, так как участники работали в разных, не пересекающихся папках (`task-service/` и `notification-service/`).
4. Открыт финальный Pull Request **`dev → main`** для релиза. Именно на этом шаге GitHub показал:
   > This branch has conflicts that must be resolved

## Описание конфликта

**Файл:** `README.md`

**Причина:** ветка `main` изначально содержала более раннюю, "стартовую" версию `README.md` (с базовыми инструкциями запуска через терминал, добавленную Tech Lead'ом при создании репозитория), в то время как в ветке `dev` этот файл к моменту финального PR был обновлён — переписан с учётом фактического способа работы команды: подробное описание запуска обоих сервисов, пример end-to-end теста через Swagger и полное описание git-flow (ветки, PR, ревью) без обращения к терминалу для git-операций.

Так как один и тот же файл менялся независимо в обеих ветках после их расхождения, Git не смог автоматически определить, какую версию считать актуальной, и пометил файл как конфликтный:

```
<<<<<<< main
(старая версия README — краткие инструкции запуска)
=======
(версия из dev — подробная инструкция, состав команды, пример
end-to-end теста, описание git-flow через сайт GitHub)
>>>>>>> dev
```

## Принятое решение

Команда решила оставить **версию из `dev`** целиком, так как она:
- актуальнее отражает реальный процесс работы (веб-интерфейс GitHub вместо терминала для всех git-операций);
- содержит пошаговую инструкцию запуска обоих сервисов и пример проверки через Swagger, которой не было в исходной версии;
- включает таблицу с распределением ролей и описание итоговой схемы веток.

Конфликт был разрешён через встроенный редактор GitHub:
1. Открыт Pull Request `dev → main`.
2. Нажата кнопка **Resolve conflicts**.
3. В редакторе удалены строки-маркеры `<<<<<<< main`, `=======`, `>>>>>>> dev`, оставлена версия из `dev`.
4. Файл отмечен кнопкой **Mark as resolved**.
5. Нажата **Commit merge** — фиксация разрешения конфликта.
6. Так как ветка `main` защищена правилом с обязательным ревью (Require a pull request before merging), PR был дополнительно одобрен вторым участником команды (**Review changes → Approve**).
7. После этого стала доступна кнопка **Merge pull request** → **Confirm merge** — финальный релиз в `main` состоялся.

## Итог

После разрешения конфликта и мерджа в `main` репозиторий содержит:
- `API_CONTRACT.md`, `README.md` (актуальная версия), `REPORT.md`;
- `task-service/` — реализация Участника 2;
- `notification-service/` — реализация Участника 3.

Оба сервиса запущены локально и проверены сквозным (end-to-end) тестом: созданная через `POST /api/tasks` задача успешно доставлена вебхуком в Notification Service и зафиксирована в `GET /api/notifications`.

## Выводы

Конфликт в данном случае возник не из-за одновременной разработки бизнес-логики (feature-ветки не пересекались по файлам и смержились в `dev` чисто), а из-за того, что документация верхнего уровня (`README.md`) обновлялась в обеих ветках независимо после их расхождения от `main`. Это показало команде, что даже "неопасные" файлы вроде README нужно синхронизировать так же внимательно, как и код — например, договариваться заранее, кто и когда вносит правки в общие файлы верхнего уровня, чтобы не редактировать один и тот же документ параллельно в разных ветках.
